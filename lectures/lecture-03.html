01

Delete, Truncate and Drop

Quick recap: DELETE FROM film WHERE film_id = 1; removes the rows matching the condition, looping over the table and deleting each match. Without WHERE, every row goes. (There is one advanced form of DELETE that needs joins; we'll meet it after joins.)

Two more commands remove data, and they are very different:

TRUNCATE film;      -- empty the table
DROP TABLE film;    -- destroy the table itself

DELETE

Removes rows one by one. Table structure stays. Slower. Doesn't reset the auto-increment id. Can be rolled back (before commit).

TRUNCATE

Drops the whole table and recreates it empty. Much faster. Resets the id counter. Cannot be rolled back.

DROP

Removes rows and the table structure. Nothing is left; you must recreate it from scratch. Cannot be rolled back.
Analogy: A register of 5 pages. DELETE = erasing entries with a pencil eraser, line by line (slow, but you kept a log so you can restore them). TRUNCATE = throwing the register away and buying an identical blank one whose page numbers restart at 1 (fast, no log of what was in the old one). DROP = burning the register and the printing plate, so no blank copy exists.

Why can't TRUNCATE be undone? A rollback needs a log of what changed. DELETE records each removed row; TRUNCATE deletes the whole table as an intermediate step and keeps no such record. Rollbacks only work for transactions that haven't been committed yet; we'll study them properly in the Transactions class. Once something is committed, SQL has no "undo".

02

LIKE: searching inside text

Equality (=) needs an exact match. But when you type "love" in a search bar you expect every title containing it. That's LIKE, the pattern-matching operator for string columns.

SELECT * FROM film WHERE title LIKE '%LOVE%';
SELECT * FROM batches WHERE name LIKE '%Academy%';

Patterns use two wildcards:

% matches any number of characters, including none.
_ matches exactly one character, whichever it is.

So 'cat%' means "starts with cat", '%cat' "ends with cat", '%cat%' "contains cat", '_at' "any one letter, then at", 'c%t' "starts with c and ends with t". Type any pattern below.

Analogy: % is a blank tile that can stand for any word length; _ is a Scrabble blank that stands for a single letter. Search suggestions (type "ca…" and see "cat", "car") are prefix patterns like 'ca%'.

03

COUNT: counting values, not rows

An aggregate function takes many values and returns one. COUNT(column) returns how many values are in the column. You'd think that equals the row count, but aggregates ignore NULLs.

SELECT COUNT(batch_id) FROM students;

Try it on this table. Rows: 4. But one student has no batch:

idnameagebatch_id

COUNT(batch_id) is 3 because only three cells hold a value. COUNT(*) counts rows regardless, which is how you get the true number of rows.

Analogy: Counting how many students submitted an assignment. A blank submission (NULL) isn't a submission, so it isn't counted even though the student is on the roll.

As a loop, COUNT is just a counter that only goes up for non-null values:

count = 0
for row in students:
    if row.batch_id is not None:
        count += 1
print(count)

Important consequence: at the end of the loop only count survives; the individual rows are gone. So with an aggregate you can print only aggregate results. SELECT COUNT(batch_id), batch_id FROM students; is invalid: there is one count but many batch_ids, so what would the second column show?

04

LIMIT and ORDER BY

ORDER BY: sorted output

SELECT * FROM film ORDER BY title;               -- A to Z (ascending, the default)
SELECT * FROM film ORDER BY title DESC;          -- Z to A
SELECT * FROM film ORDER BY title, release_year; -- title first, year breaks ties

With several columns, the later ones are tie-breakers: the year only matters between rows with the same title. Each column can have its own direction. Remember Lecture 1: without ORDER BY, row order is not guaranteed. This is how you get guaranteed order.

LIMIT and OFFSET: taking a slice

  
SELECT * FROM film LIMIT 10;             -- first 10 rows
SELECT * FROM film LIMIT 10 OFFSET 10;   -- 10 rows, starting from the 11th
SELECT * FROM film ORDER BY title LIMIT 10;

  
LIMIT n caps the rows returned; OFFSET m skips the first m. In MySQL, OFFSET can't be used without LIMIT. Since LIMIT works on the final list, it comes after sorting: "the first 10 by title" really are the alphabetically first 10.

  
Analogy: Google shows 10 results per page. Page 1 is LIMIT 10; page 2 is LIMIT 10 OFFSET 10; page N is OFFSET (N-1)*10. Every "load more" feed uses this idea.

The order things really happen

  
Think of the query as a pipeline. Press the button to step through it.

  
1
FROM + WHERE
Loop over the rows and keep only those passing the condition.
2
ORDER BY
Sort the kept rows. Every column is still available at this point.
3
SELECT
Now pick the columns to output (and remove duplicates if DISTINCT).
4
LIMIT / OFFSET
Slice the final list of rows.

  
Two rules fall out of this. 1) Because sorting happens before column selection, you can sort by a column you don't display: SELECT title FROM film ORDER BY release_year; is valid. 2) With DISTINCT it's different: after duplicates are removed you can only sort by selected columns.

  
SELECT DISTINCT title FROM film ORDER BY release_year;  -- error
SELECT DISTINCT title FROM film ORDER BY title;         -- fine

  
Why? Suppose "ACE" exists for 2006 and 2012. DISTINCT collapses them into one "ACE" row, so which release_year should place it: 2006 or 2012? The answer would be ambiguous, so SQL refuses.

JOINs: stitching tables together

  
So far every query used one table. But real questions span several. From Lecture 1, students and batches are separate tables, linked by batch_id. Now someone asks: print each student's name with their batch name. The names are in students; the batch names are in batches. No single table has both, so we need to join them.

  
A join stitches a row of one table to a row of another where a join condition is true. Here: the student's batch_id equals the batch's batch_id. Click a student to see the match, then run the join.

  
student_idfirst_namebatch_id
batch_idbatch_name

    
Click a student row…

     
    
first_namebatch_name

  
SELECT students.first_name, batches.batch_name
FROM students
JOIN batches
ON students.batch_id = batches.batch_id;

  
Line 1 chooses columns, prefixed with their table so it's clear where each comes from. FROM students JOIN batches says which two tables to combine. ON is the join condition: only rows satisfying it are stitched.

  
Analogy: Your hall ticket lists an exam-centre code; a separate notice board maps each code to a centre name. To learn where you write your exam, you match your code against the board. A join does that for every student at once.

  
As a loop, imagine trying every student row against every batch row and keeping the pairs where the condition holds:

  
for s in students:
    for b in batches:
        if s.batch_id == b.batch_id:
            output(s.first_name, b.batch_name)

  
(Databases do this far more cleverly, but the result is the same. Only rows with a match appear, so a student with no batch, or a batch with no students, is left out; we'll refine that in the next lectures.)

  
Sakila example, and aliases

  
Every film with its language, first in full, then with aliases, short nicknames given with AS so you don't retype long table names:

  
SELECT film.title, language.name
FROM film
JOIN language
ON film.language_id = language.language_id;
SELECT f.title, l.name
FROM film AS f
JOIN language AS l
ON f.language_id = l.language_id;
