GROUP BY and HAVING

Aggregate functions gave us one number for the whole table. GROUP BY gives us one number per group. HAVING then decides which groups make the cut.

01

From one number to many

In Lecture 3, COUNT, AVG and friends collapsed an entire table into a single value: total students, average marks. But often we don't want one number for everyone, we want one number per category: how many students are in each batch, the average marks of each batch, and so on.

GROUP BY is what makes this possible. It splits a table into smaller buckets, one bucket per distinct value of the column you group by, and then runs the aggregate function separately inside each bucket.

Analogy: Sorting a deck of exam sheets into piles by class section before counting each pile. Without sorting, you can only say "200 sheets total". After sorting into piles, you can say "Section A: 40, Section B: 55, ...". GROUP BY is that sorting step, done automatically.
02

GROUP BY in action

Our table for this lecture: 9 students spread across 3 batches.

SELECT COUNT(*), batch_id
FROM students
GROUP BY batch_id;

GROUP BY batch_id gathers every row with the same batch_id into one group, and COUNT(*) is then computed separately for each group, giving one count per batch instead of one count for the whole table.

03

The one rule: what can you SELECT?

Once GROUP BY runs, the table no longer exists as individual rows, only as groups. So the SELECT clause is only allowed to mention:

1. The column(s) you grouped by. Every row inside a group shares the same value there, so it's safe to print.
2. Aggregate functions like COUNT, AVG, SUM, MIN, MAX, computed over each group.

Any other raw column is ambiguous: a group can contain many rows, each with a different value for that column, so which one would SQL print? This is exactly the same reasoning from Lecture 3 about aggregates and non-aggregated columns together, just extended to groups.

GROUP BY on multiple columns

A join + GROUP BY example

Task: print every actor's name with how many films they've acted in. This needs a join (actor details and film-acting records live in different tables) before grouping:

SELECT a.first_name, a.last_name, COUNT(*) AS count_movies
FROM actor a
JOIN film_actor fa
  ON a.actor_id = fa.actor_id
GROUP BY a.actor_id;

The join first stitches every actor to each of their film credits (Lecture 3/4); GROUP BY then buckets those stitched rows by actor, and COUNT tallies each bucket. Note we group by a.actor_id (unique per actor), which is enough to also safely print first_name and last_name alongside it, since every row for one actor_id shares the same name.

A simpler single-table case: table user_classes(user_id, class_id, attended), where attended is 0 or 1. Find each user's attendance rate:

SELECT user_id, AVG(attended)
FROM user_classes
GROUP BY user_id;

Grouping by user_id buckets a user's classes together, and AVG(attended) turns each bucket's 0s and 1s into a fraction, exactly their attendance rate.

05

HAVING: filtering the groups themselves

Task: two tables, Students(id, name, age, batch_id) and Batches(id, name). Print only the batches with more than 100 students, along with their student count.

SELECT COUNT(S.id), B.name
FROM Students S
JOIN Batches B ON S.batch_id = B.id
GROUP BY B.name
HAVING COUNT(S.id) > 100;

GROUP BY B.name forms one group per batch and counts its students. HAVING then looks at those per-group counts and keeps only the groups where the count exceeds 100, discarding the smaller batches entirely, group and all.

Analogy: A class monitor sorts students into groups by house (GROUP BY), counts each house, then the principal only calls out houses with more than 50 members for the inter-house trophy (HAVING). Houses with fewer members aren't even mentioned.

The full pipeline, and WHERE vs HAVING

  
Putting everything from this course together, a query with joins, filtering, grouping and sorting executes in this fixed order, regardless of the order you type the clauses in:

  

  

  
  
The key distinction: WHERE filters individual rows, before grouping happens. HAVING filters whole groups, after grouping happens. This is also exactly why WHERE salary > AVG(salary) style conditions don't work in WHERE (more on this with subqueries in a future lecture) — WHERE runs before any aggregate is computed, row by row, so it has no concept of a group's total or average yet.

  

    
WHERE: works on raw rows, cannot use aggregate functions, runs first.

    
HAVING: works on already-formed groups, built specifically to use aggregate functions, runs after GROUP BY.

    
Rule of thumb: filtering on a raw column (age, batch_id, rating) → WHERE. Filtering on a computed group total (count, average, sum) → HAVING.

  

  






  07
Quick recap

  
    
  
  • GROUP BY buckets rows by shared column value(s); an aggregate then runs separately per bucket.
    • 
  
  • SELECT may only show grouped columns and aggregate functions, nothing else.
    • 
  
  • Grouping on multiple columns buckets by the whole combination, not each column separately.
    • 
  
  • HAVING filters the groups themselves, using aggregate conditions; it runs after GROUP BY.
    • 
  
  • Pipeline order: FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.
