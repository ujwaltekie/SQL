01

Why not just use files?

A database is an organised collection of related data: a student list, a bank's accounts, Instagram's posts. A DBMS (Database Management System) is the software that stores it and lets you Create, Read, Update and Delete it (CRUD) safely and fast.

Imagine storing everything in CSV files like this:

namebatchmarksattendance
Naman194100
Amit28170
Aditya131100

It works for 3 rows. Tap each card to see what breaks at scale.

Analogy: Files are like keeping all your notes in a shared, unlocked cupboard. A DBMS is a library with a librarian: catalogue for quick lookup, rules on what may be shelved, and a lock on the restricted section.
Real story · Integrity

In 2020 scientists officially renamed 27 human genes such as SEPT1 and MARCH1. Why? Excel kept silently converting them into dates like "1-Sep". A 2016 study found that roughly one in five genetics papers with gene lists had been hit by this error. A spreadsheet has no rule saying "this column is text, never a date".

02

The relational model

A relational database stores data as a collection of tables (formally called relations). Each row is one record and each column is one field. A table describes either an entity, a thing like students or batches, or a relationship between entities, like student_batches (who belongs to which batch). The word "relational" means exactly this: instead of piling everything into one giant sheet, we keep small, focused tables and relate them through shared values.

Why split data into related tables?

Say we keep students and their batch details in one table:

namebatch_namestart_datemarks
NamanAUG 22 Intermediate2022-08-0194
AdityaAUG 22 Intermediate2022-08-0131
AmitAUG 22 Beginner2022-08-0181

Notice the batch name and date repeat on every row. With 5,000 students in a batch, that is 5,000 copies, and real trouble follows:

Wasted space. The same text is stored again and again.
Painful updates. Rename the batch and you must edit 5,000 rows. Miss one and the data now contradicts itself.
Accidental loss. If the last student of a batch leaves and their row is deleted, the batch's details vanish too.
Typos. "AUG 22 Intermediate" and "Aug22 Intermediate" become two different batches.

The relational fix is to store each fact once, in the table it belongs to, and connect the tables with an id:

Now a batch's name lives in exactly one row. Renaming it is a one-row change, every student instantly sees it, and deleting a student never touches batch details. A query can still join the two tables whenever you want the full picture (Lecture 3).

Analogy: A restaurant bill says "Table 4", not a full description of the table, its seats and its location. The restaurant keeps that description in one place and the bill just points to it.

The rules every relational table follows

1. One table, one subject. A table holds one kind of thing or one relationship. Students go in students, batches in batches; mixing them brings back the repetition problems above.
2. Every row is unique. No two rows may be identical in every column. If they were, you could never say which one to update or delete. Two students named Naman with the same marks are fine as long as something else, like a roll number, differs.
3. One data type per column. If marks is a number, every value is a number. This is what lets the database sort marks, compute an average, or reject "Hello" outright.
4. Values are atomic. "Atom" means indivisible: each cell holds one fact. A student with two phone numbers cannot have "9001, 9002" in one cell, because you could no longer search, count or update a single number cleanly. The proper fix (a separate table) comes in Schema Design. Some databases allow list columns, but that is outside the SQL standard and queries on them are slow.
5. Column names are unique. With two columns called name, SELECT name FROM students would not know which one you mean.
6. Order is not guaranteed. Neither columns nor rows come with a promised order. Always name your columns instead of relying on position, and use ORDER BY when order matters. MySQL usually returns rows by primary key, but that is a habit, not a promise; code that depends on it can break the day a column is added.
Analogy: "Atomic" is like one cell = one fact. You would not write "Mom, Dad, Sis" in a single contacts phone field; you'd add separate entries.

03

Keys: how a row gets its identity

Someone says "update Naman's marks to 100". What if there are two Namans? The database needs a reliable way to point at exactly one row. That is the job of keys. Think of them as three levels, each narrower than the last. We'll use a students table with columns name, email, phone, batch, marks.

1 · Super key: "any clues that pinpoint one row"

A super key is any column or combination of columns whose values are never repeated across rows. Extra columns are allowed, even useless ones.
✓ (email), (phone) · ✓ (name, email) · ✓ (name, email, marks) · ✓ (email, marks)
✗ (name), (batch), (marks) all repeat.
Adding columns to a unique column never breaks uniqueness, so one table has many super keys.

2 · Candidate key: "a super key with no wasted columns"

A candidate key is a super key where removing any column destroys uniqueness. It is the trimmed-down version.
(name, email, marks) → name and marks are dead weight → (email) is a candidate key. Likewise (phone).
Composite example, attendance(student_id, class_id, present): neither student_id alone nor class_id alone is unique, but the pair is, and dropping either breaks it. So (student_id, class_id) is a candidate key, while (student_id, class_id, present) is only a super key.

3 · Primary key: "the one candidate you choose"

A table can have several candidate keys (email, phone) but needs one official identity. That chosen one is the primary key. MySQL stores rows on disk ordered by it and returns them in that order by default.
Ideal primary keys never change and are never empty. Emails and phone numbers change, so tables usually add a dedicated column such as student_id for this job.

How they nest: every primary key is a candidate key, and every candidate key is a super key, but not the other way round.

04

Foreign keys: linking tables safely

In Section 2 we split students and batches and linked them with a batch_id column. That linking column is a foreign key: a column in one table whose values must match values in a column of another table.

Reading it: Jim's row says batch_id = 2. Go to batches, find the row with id = 2, and you land on Batch B. The table holding the foreign key (students) is the child; the table it points to (batches) is the parent.

What does it guarantee?

Without a rule, someone could insert a student with batch_id = 4 when no batch 4 exists, a link pointing at nothing. Declaring students.batch_id a foreign key of batches.id makes the database reject any value that isn't present in batches.id.

Analogy: An airline ticket carries a passenger ID. The airline's system refuses to issue a ticket for an ID that isn't in its passenger list.

Two clarifications. First, "foreign" describes a column's role, not its type: it has nothing to do with being a primary, candidate or super key in its own table. Second, it can technically point to any column of the parent, for example students.year → years.id, but it should point to the parent's primary key (or at least a unique column), otherwise one value could match several rows and the link becomes ambiguous.

The catch: what happens on delete?

A foreign key protects inserts, but deletes are trickier. Delete Batch B from batches and Jim and Jack still say batch_id = 2, which now points to nothing. They are orphans. (Changing a batch's id has the same problem: students keep the old id and the data becomes inconsistent.) Databases let you choose how to handle it:

RESTRICT

Refuse the delete while any child rows still reference the parent. Safe: you must first move or remove Jim and Jack. Best when data loss would be costly.

CASCADE

Delete the parent and automatically all its children. Convenient and always consistent, but deleting one batch silently erases every student in it. Use with care.

(The exact SQL for these comes in later lectures.) Now try it yourself. "No rule" mimics plain files with no foreign key at all, so you can see orphans appear; then switch to RESTRICT and CASCADE and delete Batch B again.

05

Quick recap

  • Files are slow, unchecked, unsafe for teams; a DBMS fixes this.
  • Relational = related tables; atomic values; no guaranteed row/column order (use ORDER BY later).
  • Super key ⊇ candidate key ⊇ primary key (the chosen one).
  • Foreign keys keep tables consistent, and deletes need a plan.
